One engine, two vocabularies

The register, the six-stage machine, the wizard and the apply step are one shared code path for every change order. What forks is the type a given order is created as — engineering or supply — which is itself constrained by the project's own type. The fork changes which parties are named, whether the 20% rate rule applies, which BOQ change types are offered, and how redistribution works. It does not change the stage count, the four decisions, or the record's six tabs.

2A supply-flavoured contract still gets the works flow

CNT-0279-EM — the electromechanical package — sits inside PRJ-0279, and PRJ-0279.Type == "construction". Its change orders (VO-06, VO-07) are therefore engineering orders, reviewed by the RE department, eligible for a rate change — not supply orders, despite the contract name suggesting otherwise.

confirmed

Both fixture rows carry a comment explaining the correction: they were originally seeded Type = "supply" — "P-159's own mistake" — and retyped to engineering, because a rate change reviewed by the RE department and fixed by the pricing committee is what an engineering order looks like; a supply order may not carry rate at all, and has no resident engineer to own the review. BR-05 & the two kinds of "redistribute"

The 20% rule, and redistribution's split personalityقاعدة الـ 20% وإعادة التوزيع

1works only the 20% rate rule

For an inc/dec line: the portion of the delta up to 20% of the original contracted quantity prices at the original rate; only the excess may carry a new, committee-fixed rate. Supply never reaches this code path — TierSplit.AppliesTo is checked against inc/dec only, and a supply order's prices are LC-fixed, so there is nothing for a committee to re-price. 

threshold = originalQty × 0.20
atRate    = min(delta, threshold)        // priced at the ORIGINAL rate
excess    = max(0, delta − threshold)    // priced at whatever rate the committee fixes

Domain/TierSplit.cs:28,31,50-64 — measured against the ORIGINAL quantity (D-01), never the current effective one.

2Two things both called "إعادة توزيع"

works BOQ-line → BOQ-linesupply beneficiary → beneficiary
movesa quantity off one line, onto a different linean allocation off one workspace, onto another — same line, same total
changes the item's total?yes on both linesno — the item's contracted qty is untouched
wizard inputpick a target BOQ item, then drawn/distributed qtya from/to/qty row per transfer, any number of rows
gateredist-no-target, redist-unbalancedSupplyRedistribution.Check — draws capped at "المتاح," per source

ChangeOrderGates.cs:99-114 · Domain/SupplyRedistribution.cs — the gate reads TransferCount to tell which of the two it's looking at, so the target-item check never fires on a beneficiary transfer and vice versa.

Open findingsملاحظات بانتظار قرار

Nothing here has been changed. Each is cited to the exact lines so it can be re-checked in one look.

gap
Incoming letter no./date can be submitted blank. The reference blocks submission without both — its own comment calls the incoming letter "the legal-counter start" for BR-12's SLA clock (03 §2.1.1 / §2.10.1). The local ChangeOrderGates.Validate has no such check, and a blank IncomingDate silently defaults to the project's data date rather than being refused. vo-wizard.jsx:169-172 (reference blockers) · ChangeOrderGates.cs (no matching gate) · ChangeOrderWizardEndpoints.cs:258-259 (the silent default) → Test protocol T6 (works) · T9 (supply)
gap
A blank delta/rate on an inc/dec/rate line submits fine. The reference refuses this explicitly — "a change type that carries a quantity/rate must actually specify one." Locally, every proposal field is nullable and nothing checks it, so a line can carry a change type with zero effect and still pass every gate. vo-wizard.jsx:186-189 · change-order-wizard.types.ts:96-110 · ChangeOrderGates.cs (full file, no such check) → Test protocol T7 (works) · T10 (supply) · T8 as a control
verify
Stage 3's fixture data may not match today's code for a fresh supply order. Full detail in The six stages — the seeded VO-08 shows stage 3 skipped; WorkflowMachine.Plan today has no code path that would skip it for any order. → Test protocol T4 / T5
verify
The wizard's works-side letter-sender dropdown doesn't match the reference's party list. Full detail in Vocabulary & parties — positions 2 and 4 are swapped and one party name changed from "resident engineer" to "design & checking consultant." → Test protocol T3
by design
The two "preceding input" letters (contractor's request, consultant's opinion) have no wizard field. They render on the record's summary tab when present (P-103's four columns), but nothing in the live wizard writes them — every order created through the running app leaves them blank. This matches the written spec's own framing: those two letters happen before the order is entered, "not workflow stages and not system users" (03 §1) — so the absence looks intentional rather than an oversight, but it's worth confirming no capture screen was meant to exist for them.
