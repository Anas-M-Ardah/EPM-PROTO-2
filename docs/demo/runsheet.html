Demo runsheet · ~30 minutes

EPM Build From Zero

Start with an empty database and build a project up to recorded progress and a disbursed payment certificate, so every figure on screen has a visible origin. Nothing is loaded from a fixture; nothing is typed twice.

workspace→ project→ contract→ bill of quantities→ schedule→ link→ progress→ budget→ certificate→ three desks

The demo lands on two numbers, and both are checkable in your head

Four bill items weighted 40 / 30 / 20 / 10, with the first activity complete and the second half done. Then one certificate for exactly what was earned, less a tenth held as retention. Physical progress is what the project card reports; the cost index is what the money says about it.

(40 × 100%) + (30 × 50%) = 55% | 550,000,000 ÷ 495,000,000 = CPI 1.11
What is verified, and what is not

Steps 01–07 carry the original sheet's claim that the sequence was run end to end; steps 01–03 were independently re-run against the API on 2026-09-02 and behaved as written. Step 05 was re-run on 2026-09-03 — the XER parsed, the version was written, and the schedule tab showed the pending-approval state over an empty Gantt exactly as described. The أبواب at step 04 and the whole “When the schedule does not appear” section were written from that run. Steps 08–10 have still not been run. Their fields, permissions, refusals and arithmetic are read directly from the endpoints (EP-FIN-02, EP-FIN-03, EP-FIN-04) and from Domain/PaymentCertificate and Domain/EarnedValue — the rules say these figures should appear, but nobody has watched them appear. Rehearse the finance act once before presenting, and trust the screen over this sheet. Every input table on this sheet was read off the form templates and the endpoints on 2026-09-03 — field by field, including which ones are actually required and which are dropdowns — so the fields and their required markers are current even where the figures downstream of them are not.

Before you start

cd api/Epm.Api && dotnet run          # API on :5080
cd web && npm start                    # web on :4300
curl -X POST http://localhost:5080/api/dev/reset

The reset leaves an empty schema. The lookup vocabulary comes back with it, so every dropdown is populated and nothing else is. Do not run load-fixture — that is the opposite of this demo. You want an empty database so the audience watches the data appear.

Present at 1440 or 1280 wide; below 1200px the module rail collapses to icons. A project you create today has no data date set, so “now” falls back to the real date — which is what the planned percentage and the audit-deadline clock are measured against.

How to read the input tables

Every step below carries a table of the exact fields on that screen. A value on a tinted monospace cell is typed or picked verbatim — click it once and it selects whole. An italic grey cell means do not type anything: the field is optional, or the system fills it. A red * marks a field the server refuses without, not merely one the form nags about. Amounts are written without separators, because that is what the fields accept.

Field names are given in Arabic because that is what is on screen. Every dropdown says so in its Notes column — those you pick, never type.

How to enter the الباب — the field that is easy to skip

الباب is a select on the add form and it starts at — بدون باب —, so a bill entered quickly gets no divisions at all. On BQ-001 pick the last option, + باب جديد…, and type الأعمال الإنشائية into the name field that appears. From BQ-002 onward the باب is already in the list — pick it, do not retype it, or you will end up with two divisions spelled the same.

Do not reuse the contract's name (الأعمال المدنية) as the باب. One باب over all four lines renders a single header carrying 100% of the bill, which groups nothing and makes the hierarchy look broken rather than empty.

The three أبواب are the same three the schedule brings in at step 05 — demo-schedule.xer files its four activities under الأعمال الإنشائية, أعمال العمارة and الأعمال الكهروميكانيكية. Entering them here means the bill and the Gantt read the same structure, and step 06's links run straight down it.

Derived, not typed

Amount = quantity × rate. Weight = the item's amount ÷ this contract's bill total. Weights are rounded by largest remainder so they sum to exactly 100.00 — never 99.99. The denominator is the contract's rows, not the project's; totalling the project and then filtering is the classic version of this bug.

A باب subtotal is derived the same way and stored nowhere. The header row carries the division's item count, amount, weight, link count and rolled-up progress — but no original quantity and no variance, because a باب is a label on lines, not a record with figures of its own. Nothing in the database has a division table; grouping is BoqItem.Division and the endpoint's GroupBy.

What the الباب buys you on screen

The register becomes a collapsible باب → item grid: click a header to fold its lines away. Sorting then happens inside each باب and never across them — a heading whose rows sorted out from under it would be a heading over the wrong lines. Divisions appear in first-appearance order, so the order you type them in is the order they read in.

The الباب is optional by design: a line left at — بدون باب — is still a line, and unfiled rows render after the groups rather than disappearing. If you want to show that, leave BQ-004 unfiled, look at the register, then edit it back.

Two emptinesses, two messages — 04 §9 on screen

The file name and the activity count are printed as the proof it landed, and the last line stands where the اعتماد button will be once you switch persona. An untouched contract says something different — «لا جدول زمني لهذا العقد … حمّل بيانات العرض للبدء» — because "nothing was imported" and "the import is waiting for a signature" are not the same emptiness and must not offer the same button.

Until 2026-09-03 this screen printed the empty-database message here, contradicting the pending bar directly above it, and it was the single likeliest way to conclude an import had failed. If you are showing an older build and you see «حمّل بيانات العرض للبدء» under a warning bar, that is the old bug and not a failed import — do not import again because of it.

Submit once. A second submission is not idempotent

Each تأكيد وتقديم writes another pending version, and nothing supersedes the earlier one — submit twice and the contract carries versions 1 and 2, both مقدَّم, while the bar shows only one of them. Approving the wrong number at step 06 would then baseline the older file. If you have more than one, approve the highest number and say so.

You can always check from a terminal, and it is a fair thing to show: 

curl -s http://localhost:5080/api/projects/PRJ-0001/schedule/CNT-DEMO-01/import/versions

Each entry carries its no, its state (submitted · approved · superseded), the file name, the activity count, and the contract finish before and after. If state reads submitted, the import worked and is simply waiting for a second person.

Separation of duties — a beat, not a bug

The specialist who submits a baseline may not approve it. Try it and read the refusal aloud: the baseline is what slip and penalty are measured against, so the resident engineer owns it. Two separate rules are in force here and both are checked on the server — the party must be دائرة المهندس المقيم or مدير المشروع, and the approver must not be the person who submitted. Signing in as a resident engineer who submitted it themselves still fails, which is the point.

What the impact screen is telling you

On a first import every row reads مضاف and the contract finish delta is 0 — there is no schedule in force to move. The screen earns its place on the second import, where it names every activity whose baseline finish shifts, and every activity the new file omits. An omitted activity is never deleted: it carries bill links, progress and earned value, and the wizard names it so a person decides rather than a file.

Approving writes the plan, and only the plan

It sets the id, name, WBS, baseline dates, duration, cost, hours, milestone flag and predecessors. It does not touch progress, actual dates, float, criticality or the forecast finish — those belong to the schedule in force, and an activity that is already 82% built stays 82% built. A re-import is a re-baseline, not a reset. Everything is at zero right now, so the distinction costs nothing here and matters enormously on a live contract.

The net, computed twice on purpose

Derived, not typed

The net is gross less retention less advance recovery — the wizard shows it as a preview, and the server computes the binding one from the three figures, so a typed net could never disagree. The certificate number is the next sequential one on this contract; no code is invented.

If they ask

Why does the bill have أبواب at all?

Because a ministry bill is read by division before it is read by line, and a باب subtotal is the figure a manager actually quotes — 70% of this contract is structural work. It costs one select on the add form and it is stored as a plain label on the item; there is no division table, no division id and no second place for the same total to be wrong in.

Why is the financial percentage lower than the physical one?

Because a tenth of the certificate is retention, held until the works are accepted. The contractor has earned 550 million and been paid 495. That gap is the retention doing its job, and it is why certified and paid are two different columns everywhere in this system.

Could one person have done all of that?

No, and the refusals are server-side, not hidden in the interface. Five switches across four personas: the centre defines the workspace, the specialist defines the work, the resident engineer owns the baseline and the claim, and the finance directorate owns the budget and the money. Each refusal you saw is the rule stating itself.

Why does the strip say بدأت and not معتمد?

ملحق الشكل 4 shows 4/8 معتمد. This system has no per-module approval state — it was removed from المسار 1 and المسار 2 at the client's own instruction. Calling a unit approved because it merely holds rows would be a fabricated verdict on the first screen a manager opens, so the strip counts what it can actually know.

Can we change a quantity after this?

Only through a change order, and that is the next demo. The 20% rule is per bill line, measured against the original quantity — and the original is never overwritten. Approving an order changes nothing; applying it moves the quantities, the dates and the penalty baseline.

What happens if a desk sits on the file?

Each stage carries a time cap measured against the data date, and a breach escalates automatically — the مهل التدقيق tab is where that is visible. Since this project has no data date, the clock runs against today, so nothing will have breached during a thirty-minute demo. Say it rather than show it.
