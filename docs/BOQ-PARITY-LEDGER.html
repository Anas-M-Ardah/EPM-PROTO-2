BOQ Parity Ledger

Where the bill of quantities in this build agrees with the prototype at infinite-azaiton.github.io/epm, where it does not, and the order to fix it in. The arithmetic already matches. What does not match is everything the project type is supposed to change.

One project says both of these about itself, right now

PRJ-0439 — تجهيز الأجهزة المختبرية العلمية, the fixture's only equipment project. Its supply register reports seven line items and 505 of 762 devices received. Its progress screen and its project card report nothing at all, because on this build progress can only arrive through a schedule activity, and a delivery of microscopes has no activities.

Σ(amount × received %) ÷ Σ amount = 63.56% | what the card reports = 0%

Two places this build is deliberately stricter

The register is contract-scoped and its weight denominator is the contract's rows; the live prototype's DModBOQ renders d.boq whole and divides by the project. 02 §1 is explicit that the denominator is the contract's, and names the project-wide version as the classic bug. The divergence is correct and stays.

Receipts carry two ceilings — warehouse against what is still owed, preliminary against what has actually arrived (Domain/SupplyReceipts). The prototype has no ceiling at all. Keep ours.

The divergence ledger

Ten findings, worst first. The letters are what the plan underneath refers to, so passes can be reordered without renumbering anything.

A
blocks the demo verified

A supply project reports 0% physical progress everywhere

This is the finding the rest of the sheet is downstream of. Physical progress on this build has exactly one route — a schedule activity's percentage, reflected onto a bill line through a link, rolled up by value. A supply project has no activities and no links, so every figure on that route is zero while the receipts screen beside it is two thirds full.

Prototype

model.js:57 intercepts every project's completion and branches on type. Supply earns by value-weighted receipts — Σ(received × price) ÷ Σ(contracted × price) — with a plain quantity ratio as the fallback for items predating the price attribute. The construction S-curve is never consulted.

This build

Domain/ProgressReflection is the only source and it reads BoqActivityLinks. ProgressEndpoints.ContractPhysical, the project rollup, PortfolioBand and the EVM tiles all sit on top of it. BoqKind is never asked.

Verified: the register returns progress: 0 and achievedAmount: 0 on all seven items and in totals; the progress headline returns physical: 0; the portfolio row returns physicalPct: null. The correct figure from that same payload is 63.56% by value, or 66.27% as a plain device count.

The fix

Make BR-04 kind-aware in one place so nothing downstream changes. A supply line's progress is SupplyStatus.ReceivedPct(effectiveQty, receivedQty) — a figure this build already computes and already prints on the same row. Feed that into the existing ProgressReflection.Result instead of the link sum, and Rollup produces the contract, project and portfolio figures untouched.

Value weighting then falls out for free: Rollup is already Σ achieved ÷ Σ amount, which is the prototype's Σ(received × price) ÷ Σ(contracted × price) written the other way round. Do not add a second rollup.

B
blocks the demo verified

Every supply line reads غير مخصص, on a bill where assignment is not the mechanism

The supply register carries the works bill's coverage vocabulary. With no links on any line all seven come back unassigned and the status counter says so — which reads as seven unfinished setup tasks rather than as a column that does not apply to this kind of bill.

Prototype

DModSupplyBOQ has three facets — الفقرات التجهيزية, الاستلامات, استعلام الفقرات — and no assignment view at all. Coverage is not a concept a supply bill has.

This build

Coverage, SharesTotal, AssignedWeight and Links are computed on both kinds. CountByCoverage comes back { unassigned: 7 }, and the assignment endpoint answers 200 on the supply contract with 0 activities.

The fix
  • On kind == supply send Coverage: "na" and an empty CountByCoverage, so the register drops the chips rather than printing a zeroed set of them. 04 §9's rule — a figure that cannot be derived says so — applies to a column as much as to a tile.
  • Refuse EP-BOQ-07 on a supply bill with the bilingual shape BoqKind.Unsupported already establishes, instead of returning an empty success.
C
blocks the demo verified

The 20% rule and لجنة تثبيت الأسعار are applied to supply orders

The wizard already tells the user this rule does not apply — chg_w_tier_supply reads «أسعار الفقرات التجهيزية مثبَّتة بالعقد وخطاب الاعتماد، فلا تنطبق قاعدة الـ20% ولا لجنة تثبيت الأسعار». The server then applies it anyway. A screen that states a rule and a chain that contradicts it is worse than either alone.

Prototype

vo-wizard.jsx:107 — tiered = !isSupply && (chg === 'inc' || chg === 'dec'). :222 — needsRate = !isSupply && (anyExceeds || …), and the rate-fixing stage is spliced into the chain only when that is true. model.js:731 sets hasRateRule: false for supply outright.

This build

ChangeOrderRecord.For splits on inc / dec with no knowledge of the order's type, so LinesOverTier can be non-zero on a supply order, and WorkflowMachine.Plan then marks تثبيت الأسعار applicable.

Verified on VO-06 (type: "supply"): stages[2] is تثبيت الأسعار with applicable: true, a recorded decision, and the note «تثبّت سعر الكمية الزائدة عن 20%».

The fix

Thread one boolean; do not duplicate the arithmetic. TierSplit.AppliesTo(changeType) becomes AppliesTo(changeType, isSupply) and returns false for supply; ChangeOrderRecord.Line carries the flag so For takes the untiered branch — the same branch rate, del and redist already take. LinesOverTier is then zero by construction and Plan skips the stage with its existing reason string. Nothing else moves.

D
blocks the demo verified

A supply order can change a unit rate — the API accepts it and the fixture ships one

Supply prices are fixed by the contract and the letter of credit. No party has the standing to move one inside a change order, which is why the prototype removes the control rather than validating it afterwards.

Prototype

vo-wizard.jsx:57 — CHG_USE = isSupply ? CHG.filter(c => c[0] !== 'rate') : CHG. Four change types on a supply order, five on an engineering one.

This build

The Angular wizard filters the same way (change-order.wizard.ts:138) — but the filter is client-side only. VO-06, seeded type: "supply", carries a line BQ-002 with changeType: "rate" and a rate moved from 14,032,750 to 14,345,250.

The fix
  • Refuse rate lines on a supply order in ChangeOrderGates, where the other cross-type refusals already live. 05 §5's rule is that a refusal is server-side or it is decoration.
  • Re-seed VO-06 and VO-07. They sit on CNT-0279-EM, a contract inside a construction project, so the honest correction is to retype them engineering — which is what they are — and let finding F supply a real supply order.
E
wrong flow read

The wizard offers an engineering order on an equipment project

Prototype

vo-wizard.jsx:76 — on a supply project KINDS holds a single entry and kind initialises to 'supply'. The choice does not exist, because the project already made it.

This build

type = signal('engineering') unconditionally, and both buttons render on every project. An equipment project can raise an engineering order with a resident engineer it does not have.

The fix

Derive the offered set from the project type in the wizard's source payload, not in the component: equipment → supply only, preselected; construction → both, default engineering. Server side, refuse a mismatched type on submit. This is the same shape as BoqKind.ForProjectType and should sit beside it.

wrong flow verified

There is no supply change order on the supply project

G
wrong flow verified

A supply order still names a resident engineer

There is no resident engineer on a pure supply contract. The reviewing party is لجنة الفحص والاستلام and the requesting party is المجهز, not المقاول. Half of this is ported.

Prototype

model.js:722 voTerms is a single function returning the whole vocabulary per type — requester, reviewer, techParty, stage1Note, execNote, parties, typeLabel. Every type-dependent string in the wizard and the record reads from it, so none can be missed.

This build

WorkflowMachine.StagesFor(supply) swaps the two stage owners correctly — and that is all. VO-06 returns responsibleParty: "دائرة المهندس المقيم". The proposal columns are the fixed strings chg_party_contractor (مقترح المقاول) and chg_party_redept, with no supply variant. The rate column header switches on "every line is a rate change" rather than on the order's type.

The fix

Port voTerms whole, as Domain/OrderTerms.For(isSupply), and send it on the record and wizard payloads. One function is the point: it is what makes a missed string impossible rather than merely unlikely — the same reason BoqKind is a map and not an if in an endpoint. Angular then reads these labels from the payload instead of from lang.ts constants, because they are a rule, not copy.

H
wrong flow read

The progress tab shows a construction screen on a supply project

Prototype

DModSupplyProgress is its own screen: four figures (نسبة الاستلام as physical, نسبة التجهيز, financial, item count), a per-item receipt table, and a callout saying dates and the critical path live in the Schedule tab instead.

This build

Once A lands the headline figures stop being zero and this becomes cosmetic rather than misleading — which is why it is sequenced after A and not before it. The screen still needs its supply variant: drop the activity and WBS panels, add نسبة التجهيز beside نسبة الاستلام, and state where the delivery programme is read.

I
state it, don't build it verified

The supply project has no delivery programme

The prototype runs supply through the same schedule engine — Gantt, float, baseline against forecast — over a procurement activity set: الإحالة والتعاقد → فتح الاعتماد المستندي → التصنيع → الشحن → التخليص الكمركي → الاستلام المخزني → الفحص → التوزيع → الاستلام النهائي, with its own milestones. The difference is the activity set, not the engine.

This build seeds no activities on CNT-0439, so the tab is empty and the delayDays: 46 on its progress headline comes from contract dates alone. Defensible — the import path is the one step 05 of the runsheet demonstrates — but it has to be said out loud rather than discovered on screen.

The fix

Either a second XER beside docs/demo/demo-schedule.xer carrying the nine procurement activities, or an explicit line in the runsheet and on the tab's empty state. The XER is a day; the sentence is an hour. Ship the sentence for this demo.

J
state it, don't build it read

The third project type has no project to prove it

BoqKind.ForProjectType("design-studies") returns none and Unsupported carries a written bilingual refusal — «مشاريع التصنيف (التصاميم والدراسات الفنية) لا تملك حساب كميات في هذه المرحلة». No fixture project is typed that way, so the refusal has never been rendered.

This is the client's own three-way split (D-13), narrower than the prototype's eight display types and its single behavioural supply boolean. The mapping is sound — construction ↔ construction, equipment ↔ supply — and the third is genuinely new, which is exactly why somebody should look at its empty state before a client does.

The fix

One fixture project typed design-studies with a contract and no bill. A dozen lines, and the only way to see the refusal BoqKind was written to produce.

The plan

Until pass 1 lands, do not open a supply project in front of a client

The register is correct and the receipts screen is correct; the card and the progress tab say the project has not started. No narration survives being asked about that, and "the supply path is next week's demo" is a much better sentence than the one that follows the question.
